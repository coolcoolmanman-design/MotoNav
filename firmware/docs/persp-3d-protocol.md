# P3D：高德原生 3D 底图协议（musicA.163 起）

## 1. 为什么固件还要做一次「重投影」

目标是不让 ESP32 再逐像素挤楼块，而是让高德把带透视的 3D 鸟瞰图直接渲染出来。但有一件事必须说清：

**透视图和相机位置是绑定的。** 车往前 10 m，同一栋楼对应的屏幕行就变了，近处变得多、远处变得少。
所以「一张透视图直接平移贴屏」只能在车停着的时候成立，一动就错位；「纯贴图 + 固件只挪像素」也不成立。
固件确实还要参与，但只需要：

- 每屏行算一次前方距离 `u`（沿用现有 `t3dD/t3dPy/t3dSpan` 的单应模型，保证导航线、车标、测速牌与底图同一套透视）；
- 用随帧下发的 LUT 把 `u` 查成画布行 `v`、以及该距离处「一个画布列 = 多少米」；
- 行内按常数步长横向取样。

即：**每行一次查表 + 一次等步长横向拷贝**，没有楼块检测、没有楼高挤出、没有逐像素透视除法。
这条路的好处是楼块、楼侧面、立交桥、远近收缩全部由高德画，同时导航线和底图天然对齐（都走固件的 `u` 映射）。

## 2. 包结构（BLE bulk **type 13**）

小端，全部字段固定偏移：

| 偏移 | 类型 | 字段 | 说明 |
|---:|---|---|---|
| 0 | char[4] | magic | `'P','3','D','1'` |
| 4 | u8 | version | 1 |
| 5 | u8 | flags | bit0 = 带 16 色调色板 |
| 6 | u16 | frame | 帧号（诊断用） |
| 8 | u16 | w | 画布宽（8…1024） |
| 10 | u16 | h | 画布高（8…1024） |
| 12 | i32 | anchorX | 渲染时相机正下方的世界 X（米，与瓦片同一坐标系：X 向东） |
| 16 | i32 | anchorY | 同上，Y 向北 |
| 20 | i16 | bearing | 渲染朝向 ×10（度，0=正北，顺时针为正） |
| 22 | i16 | pitch | 渲染俯仰 ×10（度，诊断用） |
| 24 | u16 | dMin | LUT 起始距离（米） |
| 26 | u16 | dMax | LUT 结束距离（米），须 > 2×dMin |
| 28 | u16 | lutN | LUT 条数（2…64） |
| 30 | u16 | reserved | 0 |
| 32 | u16[16] | palette | 仅当 flags.bit0 时存在（RGB565） |
| … | u16×2×lutN | LUT | 每条 `{v, mm}`：`v` = 该距离对应的画布行号；`mm` = 该距离处每个画布列多少毫米 |
| … | u8 pairs | 像素 | `(run-1, color)` 双字节游程，`run` = 1…256，`color` = 0…15 |

像素按 **行优先** 排：`byte[i] = 行 y = i/w、列 x = i%w`；高半字节是偶数列（x=0,2,4…），低半字节是奇数列。

LUT 的距离采样建议按对数均分：`d_k = dMin × (dMax/dMin)^(k/(lutN-1))`，固件也是这样反查的
（`t = log(u/dMin) / log(dMax/dMin) × (lutN-1)`，线性插值）。

## 3. 固件采样公式（`Persp3D.h::p3dDrawRows`）

```
s  = (t3dPy() - (y+0.5)) / t3dSpan()          // 与 rasterRows3D 完全一致的屏幕行参数
u  = t3dD() * s / (1-s)                        // 前方平面像素距离（沿用原单应模型）
uc = u / sc + uPlus                            // 换算成米，并加上相机相对锚点的前向偏移
t  = log(uc/dMin) / log(dMax/dMin) * (lutN-1)
v  = lerp(LUT[t].v),  mm = lerp(LUT[t].mm)     // mm = 米/画布列
col(x) = w/2 + lPlus/mm + ((x+0.5) - CX) * (1/(sc*(1-s))) / mm
```

其中 `uPlus / lPlus` 是「当前相机位置 − 锚点」在画布坐标（前向 / 右向）上的分量，实现平移跟随。

**朝向约束**：画布只对应一个 bearing。固件在 `|viewHdg − bearing| > 8°` 时判为不可用，回退旧的
`rasterRows3D` 路径（底图还是旧的，但不会歪着画楼）。

## 4. iOS 侧实现要点

1. **相机**：复用 `AmapCaptureHost` 里的离屏 `MAMapView`，把 `cameraDegree` 设成目标俯仰（建议 45~50°），
   `rotationDegree = -bearing`（让屏幕上方 = 行进方向），中心对准当前定位点。
2. **取图**：`takeSnapshot` 后缩到 512×512 或 640×640（不要 1200²，带宽扛不住），
   量化成 16 色调色板（AMap 3D 底图颜色本来就少，调色板量化损失不大）。
3. **LUT**：对 64 个距离 `d_k` 用 `m.convert(coordinate, toPointTo:)` 把「沿 bearing 前方 d_k 米」的地面点
   投到屏幕像素，取 `y` 作为 `v`；再用左右各 20 米的两点算像素跨度得到 `mm = 20000/Δpx`。
   这一步是纯投影查询，不需要知道高德的相机内参。
4. **发送**：`BleBulkWriteQueue.replace(type: 13, id: frameId, packets: …)`，分片沿用现有 `M` 包格式。
5. **刷新策略**：车停着 / 直线巡航时，`bearing` 变化慢，一帧能用很久；转弯或驶出画布范围就重发一帧。

## 5. 带宽现实（必须先算清）

现有链路是单连接、单写、bulk 约 5 KB/s 量级（1200² 的正射瓦片能传，但要几十秒）。P3D 想做到
「车头一直朝上」就意味着 `bearing` 一变就要换图：

- 512×512、4bit、游程压缩后大致 20~60 KB → 按 5 KB/s 是 4~12 秒一帧；
- 40 km/h 过弯时，一秒内 `bearing` 就能变 20°以上。

所以首版验收目标是**静态/直线**场景（停车、等红灯、直路巡航）能出参考图那种楼块感；
真正要做车头向上的连续 3D，必须先把链路速率抬上去（BLE 2M PHY / 更大的 ATT MTU / 或改用 Wi-Fi 旁路），
否则转弯时只能靠 8° 容差硬撑。

## 6. 回退与兼容

- 没收到 P3D、或朝向差 > 8°、或解析失败 → 完全走原来的 `rasterRows3D`，行为与 musicA.162 一致；
- 普通瓦片（type 3）、矢量地图（type 1）、其它主题都不受影响；
- 首版只在 `t3dActive`（样式 15 / 16 的 3D 鸟瞰）下启用。

## 7. 屏幕直出（musicA.168，取代上面的 LUT 重投影）

flags.bit1 = 1 时：

- 画布固定 **233×233**，就是圆屏 466 的一半；固件 2× 最近邻放大，**不做任何 LUT / log / 单应计算**。
- 头部 reserved（偏移 30，u16）= 导航缩放 sc × 10000（px/m）。固件收到后把 iewScale 冻结到它，
  同时把 	3dBlend 锁为 1（透视几何与 iOS 生成屏幕图时一致）。
- 索引 15 = 「高德未覆盖」，固件按地面底色画。
- 锚点 = 发帧时车的位置；车离锚点超过 40 m 固件回退旧路径，iOS 在挪 20 m 或转 6° 时换帧。
- iOS 侧（AmapCaptureHost.warpPersp）按固件同一几何（CX=233、PY=330、D=240、sc=0.6）反推每屏像素的地面点，
  再用 convert(coordinate, toPointTo:) 投影到高德画面取像素。楼块和路网都是高德渲染的位置。
