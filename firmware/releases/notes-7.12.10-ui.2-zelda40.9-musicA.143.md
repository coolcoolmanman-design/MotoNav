# musicA.143 — 推屏提速（圆内 + 只推变化行）· 底图两核自适应分担 · 重启诊断

基线 musicA.142。FW-only，iOS 无需升级。画面逐像素与 .142 一致（只改「怎么算」「怎么推」，不改「画什么」）。

## 背景（.138 真机统计）

扁平档 11.2fps、楼块档 10.3fps；固件注释里整屏 434KB 推送约 ≈12fps。也就是说现在已经贴着「显示链路」的上限，
再优化底图计算（raster ≈40ms）几乎换不来帧数——要继续提速，必须**少推数据**，并让核心 0 少被渲染挤占。

## 本包

- **圆形分带推屏**：圆屏四角看不见，把圆按 24 行一带切成 20 个矩形，每带宽度取该带圆内最宽处。整屏推送数据量降到 ≈84%。
- **只推变化的行**：地图帧与上一帧（另一块缓冲，等于屏幕上现有内容）逐行比较，只推「第一行不同～最后一行不同」这一段，
  3D 顶部天空/雾几乎不变；两帧完全相同（比如停车平视后）一帧都不推，同时省电。
  只在 fastFlush + 未旋转 + 上一帧也是地图帧时启用；任何整屏推送（flushSync / flushRect）会让下一帧回到整圆；
  每 32 帧强制整圆推一次，万一有残影自愈。`#define BAND_PUSH 0` 可整体关掉。
- **底图两核自适应分担**：.142 是 `parallelRows` 对半劈，近处带楼块的下半（最贵）全在核心 0，而核心 0 还要推屏 + 蓝牙。
  现在第一帧按每行估算的开销切，之后每帧用上一帧两个核心各自的实测用时反馈调整分界行（`t3dMid`），
  核心 0 被推屏抢占变慢时，主核心自动多分到行。
- **推屏超时不再无故重启**：`flushWait` 的 3 秒超时原来会 `saveAndRestart("fastf")` 并永久关闭快速刷屏。
  现在只有「一次都没推成功过」才这么做；运行中偶发卡住只打印日志继续等（否则既重启，之后每帧还慢一大截）。
- **推屏任务每帧让出 1 个 tick**：核心 0 上渲染任务（优先级 3）+ 推屏（2）连续满载时，空闲任务饿死会触发看门狗重启。
- **重启诊断**：RTC 面包屑记录「最后一个阶段 / 地图帧数 / 内部堆最低」，开机串口打印 `[CRUMB] RR,原因,阶段,帧数,堆,ms`，
  异常重启（panic / 看门狗 / 欠压）还会存进 NVS；手机（或 nRF Connect）发 `#RR?` 从通知里读回。
  阶段：0..10 = MapFrame 里 profMark 序号；100/101 = 推屏开始/结束；200 = 地图帧开始。

## 怎么看效果

串口或 App 里的 `FPSSTAT S,<fps>,<drawMs>,<flushMs>,<qspiMHz>,<mapMs>,<ovlMs>,<fastDev>,<rasMs>,<cores>`：
- `flushMs`（第 3 项）应明显下降（圆内 + 跳过静止行）；
- `fps` 在 flushMs 是瓶颈时按比例上升；
- `rasMs` 不一定下降（总工作量没变），但两核更均衡、核心 0 腾出时间给推屏。
若 `flushMs` 仍然 ≈80ms 且 `qspiMHz`=40：可再试 `#q,60` / `#q,80`（已有命令，需重启；花屏就改回 40）。
